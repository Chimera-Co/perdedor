# Safety review of the Gemini batch (27 Nov 2026), fix before merging

I read all three files in full, along with the guard, support headers and registry. This is a static review only. I did not build or run anything, and I did not run clang-tidy or cppcheck. A few Windows behaviours below are from knowledge, not testing, and are marked "likely".

Two facts drive many of the findings:
- `guard.cpp` (lines 62-70) only recovers from access violation, in-page error, illegal and privileged instruction, misalignment, breakpoint, single-step, invalid handle, guard page and 0xC0000235. Any other exception continues the search, so it is unhandled and kills the process.
- `monotonic_ns()` is QueryPerformanceCounter.

## planned_design.cpp (`/home/shreyas/Documents/chimera/pd-planned_design/native/src/windows/planned_design.cpp`)

**Blockers**
- **910-927 `cuckoo_raised_exceptions`**
  - Problem: `100/zero` raises `EXCEPTION_INT_DIVIDE_BY_ZERO` and `RaiseException(0x40010008)` raises a custom code. Neither is in the guard whitelist, so the first one crashes the whole process. Even if it were recovered, the `r3.code == 0x40010008` test could never be true.
  - Fix: drop these two sub-tests, or run them in a dedicated VEH installed and removed inside the probe.
- **1341-1346 `raise_exception_inspection` and 1480-1485 `dbgprint_exception`**
  - Problem: both raise 0x40010006, which is not whitelisted, so both crash the process. If a run survived, `faulted` could never be true, so both probes would report detected on bare metal.
  - Fix: same as above. Note that `dbgprint_exception` duplicates `raise_exception_inspection`.
- **1377 `generate_console_ctrl_event`**
  - Problem: `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)` signals every process attached to the console. That includes the launching cmd/PowerShell/agent, which is a side effect on other processes. With no console, the call fails, `s_ctrl_c_handled == 0`, and the probe reports detected on a clean host.
  - Fix: remove it. If it stays, only run it when it owns a private console (`AllocConsole` and a dedicated process group), and treat a failed call as skipped.
- **1452-1460 `self_debugging_attach`**
  - Problem: the kernel denies `DebugActiveProcess` on the caller's own process (likely `STATUS_ACCESS_DENIED`). `already_debugged` is therefore true on every host, bare metal included. A call that succeeded would freeze the process.
  - Fix: use the child-attaches-to-parent pattern. Spawn a helper, have it try to attach to the parent, kill and wait for it, and report from its exit code.
- **1547 `selector_register_values`, x86 build**
  - Problem: WOW64 (the usual case for the x86 exe) has SS=DS=0x2b, but the code requires `ss == 0x23 && ds == 0x23`. This is detected on every 64-bit Windows host.
  - Fix: accept 0x2b for SS/DS/ES/GS under WOW64, or drop the segment checks except CS.
- **225-234 `nt_yield_execution`**
  - Problem: the 100 `NtYieldExecution` calls finish in about 50 µs, before `CreateThread` has even started the worker. Even with a running worker, an idle multicore host mostly returns `STATUS_NO_YIELD_PERFORMED`. All 100 calls return NO_YIELD, so this is detected by construction.
  - Fix: drop it, or only report when the status varies across calls on a pinned single CPU.
- **774-806 `cuckoo_invalid_hook_esp`**
  - Problem 1: it calls `NtLoadKeyEx` through raw inline asm with all-zero arguments, outside `guard::run`. A hook that dereferences those NULL arguments takes down the process.
  - Problem 2: on x64, `subq $0x48` leaves the stack misaligned at the call. Win64 needs 16-byte alignment, so a trampoline using `movaps` will fault.
  - Problem 3: on x64 the check `rsp_before != rsp_after` is meaningless, because the asm itself restores rsp.
  - Fix: wrap it in `guard::run`, use 0x40 or 0x50 instead of 0x48, and keep it x86-only (callee-cleanup check). Alternatively call a harmless function (e.g. `NtYieldExecution`) instead of a hive-loading API.

**Should-fix**
- **1510 `dbg_set_debug_filter_state`**
  - Problem: `DbgSetDebugFilterState(0,0,TRUE)` writes a system-wide kernel debug-print filter and never restores it. It breaks the read-only rule when the process holds SeDebugPrivilege.
  - Fix: skip it, or restore the previous state.
- **162-175 `nt_query_object_type_information`**
  - Problem: it probes invalid handle values outside `guard::run`. Where handle exceptions are enabled (debugger, AppVerifier), this raises `EXCEPTION_INVALID_HANDLE` and crashes the process (likely).
  - Problem: it also cannot detect what it claims. A DebugObject handle lives in the debugger process, not the debuggee.
  - Fix: move the loop into a guarded POD leaf.
- **861-898 `cuckoo_pid_reuse`**
  - Problem: detected is hard-coded `false`, so it always reports Clean at confidence 0.7.
  - Problem: on a 1 s timeout the child is not killed.
  - Problem: `cmd.exe` is resolved through the search path.
  - Fix: return Info or skipped, use an absolute `System32\cmd.exe`, and `TerminateProcess` on timeout.
- **622-656 `scan_modules_memory_walk_gmi`**
  - Problem: in the x86 build under WOW64, the 64-bit ntdll, wow64, wow64cpu and wow64win images are executable MEM_IMAGE but not in the 32-bit module list (likely). `GetModuleInformation` fails, so this is detected on a clean host.
  - Fix: skip when `IsWow64Process` is true, or filter those images.
- **318-323 `process_job_object`**
  - Problem: any job counts as detected. Task Scheduler tasks, OpenSSH sessions, terminals and the harness itself run processes in jobs.
  - Fix: downgrade to Info, or only flag jobs that carry limits typical of sandboxes.
- **1691 `rtt_confirm_dialog`**
  - Problem: `duration < 50 ms` is flagged as a bot. If the dialog fails immediately (session 0 or no interactive desktop, `res == 0`), the probe reports detected.
  - Fix: require `res` to be IDOK or 32000 (timed out), otherwise skip.
- **222-238, 954-970, 1414-1424 (yield, suspended-thread, suspension watchdog)**
  - Problem: the worker's context lives on the probe's stack and the join wait is bounded (500-1000 ms). After a long stall, the very case `process_suspension_detection` targets, the function returns while the worker still writes to the dead frame.
  - Fix: allocate the context on the heap and share ownership with the thread (`std::shared_ptr`).
- **1410-1437 `process_suspension_detection`**
  - Problem: it decides on a single 30 ms sample against a 300 ms threshold. `ticks` is collected but unused.
  - Fix: take several samples and use the watchdog gap.
- **1570-1627 `exclusive_create_file` and `exclusive_load_library`**
  - Problem: opening your own exe, or kernel32, with share mode 0 gets a sharing violation when Defender or an indexer has the file open, so it is detected on a clean host. For the kernel32 case, any process or loader mapping kernel32 in that instant also fails.
  - Fix: use `FILE_SHARE_READ`, or drop the probe.
- **1246-1331 `popf_and_cpuid` and `ss_register_trap`**
  - Problem: the trap fires after the first instruction following `popfq`. That is `xor eax,eax` in the CPUID probe and `mov ax,ss` in the SS probe, so CPUID and MOV SS are never stepped. They report Clean regardless of the hypervisor.
  - Fix: put the setup instruction before `popf` and the target instruction directly after it.

**Minor**
- 1161-1197 and 1246-1270: if the trap is lost, TF stays set after the guard returns (see env note).
- 1010-1012, 1076-1077: any `OpenService` failure (including access denied) is treated as "stopped" and reported detected.
- 403-404, 452-453: `EnumProcessModulesEx` is not exported from kernel32 (the export is `K32EnumProcessModulesEx`). The lookup only works because psapi is linked in.
- 1735: the wallpaper path in evidence can contain the user name.

**Verdict: ship after fixes.** There are 7 blockers, most of them guard-whitelist or by-construction detections.

## planned_env.cpp (`/home/shreyas/Documents/chimera/pd-planned_env/native/src/windows/planned_env.cpp`)

**Blockers**
- **127-153 `probe_shadow`**
  - Problem: the trap fires after `mov ax,ss` (the first instruction after `popfq`), so `shadow_stage` is always 0. `shadow_ok` is therefore false, and `hypervisor_exception_quirks` is detected on bare metal.
  - Fix: do `mov ax,ss` before `popfq`, then `popfq; mov ss,ax; movl $1; movl $2`.
- **439-466 `uefi_nvram_variables`**
  - Problem: nothing enables `SeSystemEnvironmentPrivilege`, so `GetFirmwareEnvironmentVariableW` fails with 1314. `boot_order_present` is false on every host and the result is always detected.
  - Problem: legacy-BIOS bare metal is also reported as detected.
  - Fix: enable the privilege on the own token and restore it. Skip on 1314. Do not count legacy BIOS as a VM signal.
- **908-925 `net_validate_name_emulation`**
  - Problem: this is a network=false probe. `NetValidateName` with NetSetupMachine can do NetBIOS or DNS name-conflict and DC lookups, and can block for seconds.
  - Problem: an abandoned thread keeps netapi32 loaded.
  - Fix: remove it, or mark it `network=true` and gate it on `ctx.network`.
- **877 `hosting_provider_check`**
  - Problem: it contacts the real third party `ip-api.com` over plain HTTP, which breaks the "never contact real third-party services" rule.
  - Problem: four 3 s WinHTTP timeouts can exceed the 10 s fast budget, so the probe thread is abandoned holding WinHTTP handles.
  - Problem: on a request failure (883) it returns Clean instead of skipped.
  - Fix: require an operator-supplied host parameter and skip without it. Return skipped on failure. Set an overall deadline.

**Should-fix**
- **105-125, 127-153, 156-180 (single-step probes)**
  - Problem: if the hypervisor never delivers the trap, TF stays set after the guard returns. A later trap is then unhandled and kills the process.
  - Fix: after the trapped instruction, add `pushf; and $~0x100,(%rsp); popf`. It only executes when no trap fired.
- **156-180 `probe_cpuid_step`**
  - Problem: the trap fires after `xor eax,eax`, so CPUID is never stepped.
  - Fix: move the `xor` before `popf`.
- **469-484 `thread_mismatch`**
  - Problem: `GetSystemInfo` reports only the current processor group. On hosts with more than 64 logical CPUs, `os_threads < leaf0b_threads` is detected on bare metal.
  - Problem: `cpuid(0x0B,1)` is called without checking the maximum basic leaf.
  - Fix: use `os_processors()` (all groups) and check the maximum leaf first.
- **557-558 `office_emulation_artifacts`**
  - Problem: `HKCU\Software\Microsoft\VBA` exists on real machines with Office installed, so it reports detected on bare metal.
  - Fix: drop the key.
- **815, 798 `cuckoo_agent_listener`**
  - Problem: no process has an exe name like `agent.py`, so the process check never matches. Any dev server on port 8000 triggers the port check.
  - Fix: remove the process check and downgrade the port check to a hint.
- **392-436 `tpm_measured_boot`**
  - Problem: a physical machine without a TPM is reported detected.
  - Fix: downgrade to Info, or skip when no TPM is present.

**Minor**
- 317-322, 328-334: the Hyper-V registry key and BIOS strings match every Hyper-V guest, not just Azure.
- 509-515: committing 1 GiB on a 2 GiB guest can force a pagefile grow.
- 662-677 `windefend_emulator_artifacts`: severity High and confidence 0.95 for a hostname/user-name match is overconfident.

The ept_hook_timing, gamarue_volume_serial, vmware_mutexes, vsgpu, dns_suffix and cuckoo artifact probes had no real defects. azure_cloud is network=true, contacts only 169.254.169.254, and has a 1 s timeout.

**Verdict: ship after fixes.** There are 4 blockers.

## planned_timing.cpp (`/home/shreyas/Documents/chimera/pd-planned_timing/native/src/windows/planned_timing.cpp`)

**Blockers**
- **269-281 `icmp_send_echo_delay`**
  - Problem: on Windows all of 127.0.0.0/8 is loopback, so 127.0.0.2 answers immediately. The measured time is about 0 ms, which is below the threshold of 70 ms. It is detected on every host.
  - Fix: use a non-routable address with an assured silent drop, or drop the probe. Do not use a real non-loopback destination in a network=false probe.
- **83-126 `clock_jitter_vmaware`**
  - Problem: it compares QPC against `GetSystemTimeAsFileTime` over 20 ms windows. FILETIME ticks at 15.6 ms unless the timer resolution has been raised, so the ratios jump between about 0.5 and 1.5. The drift check `drift > 0.375` trips on bare metal.
  - Fix: use `GetSystemTimePreciseAsFileTime` (or the KUSER interrupt time) and windows of at least 200 ms.
- **1226-1245 `qpc_time_delay_loop`**
  - Problem: the loop is bounded by QPC and "independent" monotonic time is `monotonic_ns()`, which is also QPC. The probe can never detect anything and reports Clean.
  - Fix: take the reference time from `GetTickCount64`, the KUSER InterruptTime, or `GetSystemTimePreciseAsFileTime`.
- **745 `external_time_tampering` default host**
  - Problem: the default host is `www.microsoft.com`, which breaks the "never contact real third-party services" rule.
  - Problem: HTTPS validation fails exactly when the guest clock is far off, so the case it targets returns unavailable. A failed `SystemTimeToFileTime` (798-799) is unchecked.
  - Fix: require an operator-supplied host, ignore certificate errors for this Date-only HEAD request, and check the `SystemTimeToFileTime` results.

**Should-fix**
- **962-964 `kernel_kuser_tick_timing`**
  - Problem: it compares the 32-bit `GetTickCount()` with the 64-bit KUSER tick. After 49.7 days of uptime the delta is about 4.29e9, so it is detected on bare metal.
  - Fix: use `GetTickCount64` as in the sibling probe at 705.
- **1060-1078 `network_adapter_reset_time`**
  - Problem: `TimeOfLastReset` is local time with a UTC offset suffix, but the code treats it as UTC. For positive-offset timezones this gives false "recent reset" hits and for others it skews the age.
  - Fix: parse the `±UUU` offset.
- **590-602 `cuckoo_infinite_delay`**
  - Problem: `data` is on the stack, and the worker may still run if the 500 ms join times out.
  - Fix: heap-allocate the context, or keep waiting until the thread exits.
- **1137-1147 `dotnet_time_delay`**
  - Problem: `powershell.exe` is resolved via the search path. `CreateProcessW` also passes TRUE for handle inheritance.
  - Fix: use the absolute `System32` path and an explicit handle list.

**Minor**
- 530-537: `guard_before` and `guard_after` can be constant-folded away, because only `&test.interval` escapes. Make the struct `volatile`.
- 840-849: a DST or clock step during the 100 ms window clamps the elapsed time to 0 and reports detected.
- 424: `sleep_loop` with a 5 ms step and 2 loops sits right at the tick granularity.

Timer-queue, waitable-timer, `timeSetEvent`, SetTimer, WaitForMultipleObjects, socket-timeout, KUSER-read and the Sleep-based probes look correct. Their handles are RAII-managed and their waits are bounded.

**Verdict: ship after fixes.** There are 4 blockers.

## Shared note
All three files compile plausibly as x86 and x64, and ids match registrations. The two `popf` single-step probes in the design and env files share one flaw: the first instruction after `popf` takes the trap. A single helper that sets TF, then runs exactly one target instruction, then clears TF would fix all of them.
